# Synthetic migration results — 27 October 2026

**Accepted scope:** a small, fresh local Pebble fixture migrated through Kubo
0.31.0 -> 0.34.1 -> 0.43.1, with explicit repository schema16->17->18 migration,
content/pin/MFS checks and independent old-generation restoration. **Not production
acceptance.** No production data, credentials, remote storage or live services
were used.

## Exact target-run evidence

- Hosted Ubuntu24.04, job **122084272266**, completed **08:22:09 UTC**.
- All **23 unit tests passed**. These are guardrails; the separate Kubo step
  supplies the actual migration evidence.
- All three official release archives passed published SHA-512 verification;
  extracted executables were independently SHA-256 checked before use.
- Kubo commands ran unprivileged with a clean environment and only loopback in
  the network namespace. No daemon was started. No external migration tool was
  downloaded from inside the test namespace.
- Old fixture: repository schema16,2MiB deterministic repeating bytes, one raw
  unpinned block, MFS reference, two recursive pins (including initial empty-root
  pin) and **zero direct pins**. Repeated content deduplicates: this is a tiny
  engine/logic test, not a large-database or compaction benchmark.
- 0.34.1 opened a separate physical copy and preserved exact payload bytes,
  recursive/direct pin sets and MFS root. Repository schema remained16; observed
  Pebble marker `marker.format-version.000015.016`.
- On a separate negative-control copy,0.43.1 `pin ls` returned exit1 with
  `ipfs repo needs migration`. This expected refusal is retained in commands.json.
- On another fresh bridge copy,0.43.1 executed exactly:
  `ipfs --offline repo migrate --to=18`.
  Output confirmed both **embedded16-to-17 and17-to-18 migrations** completed;
  repository versionfile was independently checked as18.
- Synthetic identity and full Datastore configuration plus `datastore_spec`
  remained identical across schema migration. Changed top-level config sections:
  AutoConf,Bootstrap,DNS,Ipns,Provider,Reprovider,Routing. Their production-specific
  semantics are not validated by this synthetic experiment.
- 0.43.1 then read both exact payloads and matched all baseline pin/MFS values.
  Observed target Pebble marker `marker.format-version.000023.024`.
- A separate copy of the sealed **old** generation reopened under0.31.0 and
  matched the same fingerprint. This is restore-based rollback, **not an in-place
  downgrade of the upgraded database**.
- Full original seed file hashes remained unchanged. The report records
  `bridge_verified=true`, `target_migration_verified=true`,
  `rollback_control_verified=true`, `seed_unchanged=true`,
  and `production_approved=false`.

## What this does not establish

No realistic production-size database, custom configuration, plugin layout,
corrupted SST/WAL, interrupted upgrade, forced crash, pin-stream locking or
abandoned-consumer regression has been tested. Direct-pin preservation is only
an empty-set check. Target-side new writes and daemon startup/shutdown have not
been accepted. Remote object-store caching, version selection, writeback and
retention are outside this local experiment.

No attempt to reopen the **upgraded** copy with0.31.0 was made. No supported
in-place downgrade is claimed. Keep the untouched full old generation as the
recovery control.

Next expand varied/non-deduplicating fixtures, nonempty direct pins, target writes
and reopen, cancellation/locking and interrupted migration recovery. Only then
consider a privately held consistent real-data snapshot; never publish one here.
